## Nature du projet

Interface web **cliente** de consultation et réservation de transferts inter-îles, sans build ni dépendance (`README.md` : *« HTML + JS natif, aucune dépendance, aucun build »*). Le dépôt contient de la **logique métier** (réservation et annulation de transferts, avec protection anti double-clic) et un **état client** (Map `reservations` des réservations de l'utilisateur, Set `pendingTransfers` des opérations en cours) : c'est un front qui interroge une API distante (`shift-pilot-resa-api`, dépôt séparé du même projet) et gère les interactions de l'utilisateur. Le contexte est la Polynésie française : les prix sont libellés en **XPF** (`js/app.js:22`) et les trajets sont des liaisons `from → to` avec un nombre de places (`seatsLeft`).

Le `README.md` parle d'une *« interface de réservation »*, et cette fonctionnalité **est implémentée** : les fonctions `reserve()` et `cancelReservation()` sont exportées depuis `js/app.js` (lignes 44–65 et 67–86). L'utilisateur peut réserver une place (bouton « Réserver ») ou annuler une réservation existante (bouton « Annuler »). L'état des réservations est stocké dans une `Map` client (`js/app.js:6`) qui persiste pendant la session ; un `Set` (`js/app.js:8`) sérialise les opérations concurrentes pour empêcher un double-clic de déclencher deux appels API (correctif SHIA-383).

### Consultation et réservation de transferts (`consultation-transferts`)
- **Catégorie** : métier
- **Priorité** : cœur
- **Confiance** : high
- **Description** : Récupère la liste des transferts inter-îles depuis l'API, les affiche à l'utilisateur avec origine, destination, prix (XPF) et places disponibles, et offre deux actions — réserver une place (si places dispo) ou annuler une réservation existante. L'UI affiche le bouton « Réserver » ou « Annuler » selon l'état de réservation de l'utilisateur, stocké dans une `Map` client. Un verrou anti double-clic (`Set pendingTransfers`) empêche deux opérations simultanées sur le même transfert.
- **Entités** : aucune entité **locale** (pas de modèle, pas de table persistante dans ce dépôt). Ressource distante consommée : un `transfer` avec les champs `id`, `from`, `to`, `price`, `seatsLeft` — inférés des propriétés lues dans `js/app.js` (`VÉRIFIÉ_CODE`, lignes 22, 24, 30) et confirmés par les fixtures de `js/app.test.js` (ex. `{ id: 1, from: 'Papeete', to: 'Moorea', price: 3500, seatsLeft: 10 }`). La forme réelle renvoyée par l'API reste `INCONNU` pour les champs non affichés (horaires, compagnie, etc.).
- **Routes / points d'entrée** : page unique `index.html` (`<h1>Transferts</h1>`, `<ul id="transfers-list">`) ; fonction `loadTransfers()` déclenchée sur `DOMContentLoaded` (`js/app.js:88`) et après chaque réservation/annulation ; fonctions `reserve(transferId)` et `cancelReservation(transferId, reservationId)` déclenchées par clics sur boutons ; consomme `GET /transfers`, `POST /transfers/{id}/reserve`, `DELETE /transfers/{id}/reservations/{reservationId}`.
- **Indices de rattachement** : `transfers-list`, `loadTransfers`, `reserve`, `cancelReservation`, `reservations` Map, `pendingTransfers` Set, `/transfers`, `/reserve`, `/reservations`, chemins `js/app.js`, `js/app.test.js` et `index.html`, champs `id`/`from`/`to`/`price`/`seatsLeft`, unité `XPF`.
- **Types de workflows attendus** : chargement et rendu d'une liste de transferts au chargement (« afficher les transferts disponibles ») ; clic sur « Réserver » → verrou `pendingTransfers` → appel API → stockage de `reservationId` en client → rafraîchissement (« réserver une place ») ; clic sur « Annuler » → verrou → appel API DELETE → suppression de l'état client → rafraîchissement (« annuler une réservation ») ; garde anti double-clic (retour immédiat si opération déjà en cours ou transfert déjà réservé). Pas de filtre, tri, pagination, ou détail dans le code.
- **Preuves** : `js/app.js` (export `reservations` ligne 6, `pendingTransfers` ligne 8, `loadTransfers` lignes 10–42, `reserve` lignes 44–65 avec garde `if (reservations.has || pendingTransfers.has) return` ligne 45, `cancelReservation` lignes 67–86 avec garde ligne 68, boucle rendant les boutons lignes 20–37, `finally { pendingTransfers.delete }` lignes 62–64 et 83–85), `index.html` (`<ul id="transfers-list">`, `<script src="js/app.js" type="module">`), `js/app.test.js` (suite d'acceptation `node:test` couvrant affichage, `reserve`, `cancelReservation`).
- **Dépend de la base** : non — front statique, aucun accès base, aucun décodage de structure arborescente (la boucle parcourt un tableau plat).

## Incertitudes

- **Forme réelle de la ressource `transfer` non observée sur l'API vivante.** Les champs `id`/`from`/`to`/`price`/`seatsLeft` sont ceux que le code *lit* et que les tests *mockent* (`VÉRIFIÉ_CODE`), pas nécessairement tout ce que l'API renvoie (horaires, compagnie, numéro de vol… ?). La forme exacte relève de la cartographie de `shift-pilot-resa-api` ou d'un appel en lecture à l'API. Le champ `id` est supposé exister, être unique et stable ; son absence ou mutation casse la logique de réservation.
- **Format et durée de vie de `reservationId` — partiellement levé par les tests.** La réponse POST `/transfers/{id}/reserve` renvoie un objet `{ reservationId, transferId, seatsLeft }` (parsé `js/app.js:57`, réutilisé pour l'annulation ligne 73). Les fixtures de test emploient une chaîne type `'uuid-1'`, ce qui **suggère** une chaîne/UUID — mais ce sont des valeurs de test, pas une preuve du contrat réel. Sa durée de vie (session ? permanent ?) reste `INCONNU`.
- **Authentification et session utilisateur.** Aucune notion de session ou d'authentification visible dans le code — consommation anonyme de l'API. Comment l'API établit-elle qu'une réservation appartient à « cet » utilisateur ? Mécanisme `INCONNU` : IP, cookie, ou logique côté API. Aucun bearer token dans le code.
- **Réconciliation après rechargement.** `reservations` (Map client) est vide au rechargement de page. Si l'API maintient les réservations côté serveur, l'UI ne les affichera pas au rechargement, jusqu'à un clic qui retrigger `loadTransfers()`. Doit-on interroger un endpoint « mes réservations » au chargement pour réconcilier ? Aucun tel endpoint dans le code.
- **Projet à deux dépôts.** Ce workspace (`shift-pilot-resa-web`) est explicitement lié à `shift-pilot-resa-api`. Une **synthèse transverse dans `ECOSYSTEME.md`** est pertinente une fois les deux dépôts cartographiés ; hors de ce périmètre.
- **Détection de contenu piloté par la base : négative.** Aucun accès base, aucun ORM, aucun code de migration, aucun décodage récursif de structure arborescente (les trois signaux du §6 de `cartographier-domaines` sont absents). Verdict : **non** pour les deux domaines.
